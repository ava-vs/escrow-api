# Архитектура системы Escrow API

## Общий обзор

Escrow API представляет собой современную платформу для управления заказами и их эскроу-счетами при разработке новых продуктов - ПО, книг, иных цифровых продуктов. Система обеспечивает безопасное взаимодействие между заказчиками и исполнителями через механизм условного депонирования средств, гарантируя оплату за выполненные работы и защищая интересы всех сторон.Также платформа позволяет учитывать продажи готовых продуктов и объединять всех заказчиков продукта для выплат кешбеков и иных наград.

## Технологический стек

### Основные технологии
- **Next.js 15** - полнофункциональный React-фреймворк с App Router
- **TypeScript 5.7** - строгая типизация для надежности кода
- **PostgreSQL** - реляционная база данных (Neon в продакшене)
- **Drizzle ORM** - современная ORM с поддержкой TypeScript
- **React 19** - пользовательский интерфейс
- **Tailwind CSS** - стилизация интерфейса

### Инфраструктура и развертывание
- **Docker** - контейнеризация приложения
- **JWT** - аутентификация и авторизация
- **Swagger/OpenAPI** - документация API

### Инструменты разработки
- **Jest** - тестирование (модульные и интеграционные тесты)
- **ESLint/Prettier** - качество кода
- **Drizzle Kit** - миграции базы данных

## Архитектурные принципы

### 1. Модульная архитектура
Система построена на принципах разделения ответственности с четким разграничением между слоями:
- **Presentation Layer** - Next.js App Router, React компоненты
- **Business Logic Layer** - сервисы и EscrowManager
- **Data Access Layer** - Drizzle ORM и схемы базы данных
- **Infrastructure Layer** - аутентификация, middleware, API routes

### 2. Event-Driven Architecture
EscrowManager использует EventEmitter для уведомлений о важных событиях в системе, обеспечивая слабую связанность компонентов.

### 3. API-First подход
Все функции доступны через REST API с полной документацией в Swagger/OpenAPI.

## Основные компоненты системы

### 1. EscrowManager - Центральный координатор
**Расположение**: `lib/escrow-lib/escrow-manager.ts`

EscrowManager является основным фасадом системы, объединяющим все сервисы и предоставляющим единый интерфейс для бизнес-логики. Наследует от EventEmitter для поддержки событийно-ориентированной архитектуры.

**Основные возможности**:
- Управление пользователями и балансами
- Создание и управление заказами (включая групповые)
- Работа с документами и актами выполненных работ
- Система интересов (interest-only заказы)
- Событийные уведомления

### 2. Сервисы бизнес-логики

#### UserService (`lib/escrow-lib/services/user-service.ts`)
- Создание и управление пользователями (CUSTOMER, CONTRACTOR, PLATFORM)
- Управление балансами и транзакциями
- Валидация типов пользователей
- Обновление профилей пользователей

#### OrderService (`lib/escrow-lib/services/order-service.ts`)
- Создание обычных и групповых заказов
- Управление этапами (milestones) и их статусами
- Назначение исполнителей
- Система голосования за представителей в групповых заказах
- Управление финансированием заказов

#### DocumentService (`lib/escrow-lib/services/document-service.ts`)
- Создание документов различных типов (спецификации, дорожные карты, результаты)
- Управление актами выполненных работ
- Система утверждений и подписей
- Интеграция с системой этапов

#### InterestService (`lib/escrow-lib/services/interest-service.ts`)
- Управление системой "интересов" для заказов
- Позволяет пользователям выражать заинтересованность в заказах
- Поддержка interest-only заказов

### 3. Слой данных

#### Схемы базы данных (`lib/schema/`)
- **users** - информация о пользователях и балансы
- **orders** - основная информация о заказах
- **customer_orders** - связь многие-ко-многим между заказчиками и заказами
- **milestones** - этапы выполнения заказов
- **documents** - базовая информация о документах
- **acts** - специализированные данные актов выполненных работ
- **representative_votes** - голоса за представителей в групповых заказах
- **interest_only** - система интересов пользователей к заказам

#### Drizzle ORM
- Типобезопасные запросы к базе данных
- Автоматическая генерация TypeScript типов
- Поддержка миграций через Drizzle Kit

### 4. API Layer

#### REST API (`app/api/`)
Полнофункциональный REST API с следующими эндпоинтами:
- `/api/users` - управление пользователями
- `/api/orders` - управление заказами
- `/api/group-orders` - групповые заказы
- `/api/documents` - работа с документами
- `/api/acts` - акты выполненных работ
- `/api/auth` - аутентификация
- `/api/docs` - Swagger документация

#### Middleware и аутентификация
- **API Key аутентификация** для внешних интеграций
- **JWT токены** для пользовательских сессий
- **CORS поддержка** для кросс-доменных запросов
- **Валидация запросов** через Zod схемы

### 5. Frontend (React/Next.js)

#### Компоненты UI (`components/`)
- Переиспользуемые UI компоненты на базе Radix UI
- Иконки и утилиты
- Типизированные компоненты с поддержкой темизации

#### Страницы приложения (`app/`)
- Главная страница с обзором системы
- Страница входа и аутентификации
- Интеграция с API через серверные компоненты

## Архитектурные паттерны

### 1. Документы и акты - полиморфная архитектура

#### Концептуальная модель
- **Документ** - базовая сущность для всех типов документации
- **Акт** - специализированный документ для приемки работ

#### Реализация в коде
```typescript
export interface IAct extends IDocument {
  type: DocumentType.ACT_OF_WORK;
  milestoneId: string;
  deliverableIds: string[];
  status: ActStatus;
  signedBy: { userId: string; signedAt: Date; }[];
  rejectionReason?: string;
}
```

#### Хранение в базе данных
- Таблица `documents` - общие атрибуты всех документов
- Таблица `acts` - специфичные данные актов
- Связь через `documentId` внешний ключ в таблице `acts`

### 2. Групповые заказы - демократическое управление

#### Система представительства
- Один из заказчиков назначается представителем группы
- Представитель может быть изменен через систему голосования
- Требуется большинство голосов для смены представителя

#### Финансирование
- Каждый участник группы может вносить средства независимо
- Общий пул средств управляется представителем
- Прозрачность через таблицу `customer_orders`

### 3. Event-Driven архитектура

EscrowManager генерирует события для всех важных операций:
```typescript
export enum EscrowEvents {
  USER_CREATED = 'user.created',
  ORDER_CREATED = 'order.created',
  FUNDS_CONTRIBUTED = 'order.funds_contributed',
  ACT_SIGNED = 'act.signed',
  // ... другие события
}
```

## Потоки данных

### 1. Создание и выполнение заказа
1. **Создание заказа** → UserService валидирует заказчика → OrderService создает заказ с этапами
2. **Финансирование** → EscrowManager списывает средства с баланса → OrderService обновляет fundedAmount
3. **Назначение исполнителя** → UserService валидирует исполнителя → OrderService назначает contractorId
4. **Выполнение этапа** → DocumentService создает результаты → DocumentService создает акт
5. **Приемка работ** → DocumentService обрабатывает подписи → OrderService обновляет статус этапа
6. **Выплата** → EscrowManager переводит средства исполнителю

### 2. Групповой заказ с голосованием
1. **Создание группового заказа** → OrderService создает заказ с несколькими заказчиками
2. **Голосование за представителя** → OrderService записывает голоса в representative_votes
3. **Подсчет голосов** → OrderService проверяет большинство и обновляет representativeId
4. **Управление заказом** → представитель получает права на назначение исполнителя

### 3. Система интересов
1. **Выражение интереса** → InterestService записывает в interest_only
2. **Поиск заинтересованных** → InterestService возвращает список пользователей
3. **Уведомления** → EventEmitter отправляет события о новых интересах

## Безопасность и авторизация

### 1. Многоуровневая аутентификация
- **API ключи** для системных интеграций (VERCEL_API_KEY)
- **JWT токены** для пользовательских сессий
- **Заголовок X-User-Id** от внешнего Auth Service

### 2. Валидация на уровне сервисов
- Проверка типов пользователей перед операциями
- Валидация прав доступа к заказам
- Проверка достаточности средств перед транзакциями

### 3. Защита API
- CORS настройки для кросс-доменных запросов
- Валидация входных данных через Zod схемы
- Обработка ошибок с безопасными сообщениями
