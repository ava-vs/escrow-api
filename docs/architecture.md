# Архитектура системы

## Общий обзор

Escrow API представляет собой платформу для управления эскроу-счетами при разработке программного обеспечения. Система позволяет заказчикам и исполнителям безопасно взаимодействовать через платформу, используя эскроу-механизм для гарантии оплаты и выполнения работ.

## Основные компоненты

Система построена с использованием следующих компонентов:

1. **Next.js** - фреймворк для серверного рендеринга React-приложений
2. **TypeScript** - типизированный JavaScript для более надежного кода
3. **PostgreSQL** - реляционная база данных для хранения данных
4. **Drizzle ORM** - ORM для работы с базой данных
5. **NextAuth.js** - аутентификация пользователей
6. **API Routes** - серверные эндпоинты для взаимодействия с системой

## Модульная структура

Система разделена на следующие модули:

1. **User Service** - управление пользователями, балансами и аутентификацией
2. **Order Service** - управление заказами, этапами и финансированием
3. **Document Service** - управление документами проекта и актами выполненных работ
4. **Escrow Manager** - центральный модуль, объединяющий все сервисы и предоставляющий единый интерфейс

## Взаимодействие компонентов

### Архитектура документов и актов

В системе существует особая взаимосвязь между документами и актами:

#### Концептуальный уровень
- **Документ** - это общая сущность для хранения различных типов документации
- **Акт** - это специализированный тип документа, который представляет акт выполненных работ

#### Уровень интерфейсов
В TypeScript интерфейсах `IAct` наследуется от `IDocument`, добавляя специфичные для акта поля:
```typescript
export interface IAct extends IDocument {
  type: DocumentType.ACT_OF_WORK;
  milestoneId: string;
  deliverableIds: string[];
  status: ActStatus;
  signedBy: { userId: string; signedAt: Date; }[];
  rejectionReason?: string;
}
```

#### Уровень базы данных
В базе данных документы и акты хранятся в разных таблицах:
- Таблица `documents` хранит основные данные документов
- Таблица `acts` хранит специфичные для актов данные

Связь между ними реализована через соглашение об идентификаторах:
- ID акта в таблице `acts` совпадает с ID соответствующего документа в таблице `documents`
- Это позволяет получить полные данные акта, объединяя информацию из обеих таблиц

#### Логика взаимодействия
Когда необходимо получить акт:
1. Сначала получаем базовый документ по ID
2. Проверяем, что его тип - `ACT_OF_WORK`
3. Затем получаем данные акта из таблицы `acts` по тому же ID
4. Объединяем данные для получения полного представления акта

Эта архитектура позволяет:
- Хранить общие атрибуты в таблице документов
- Хранить специфичные для актов данные в отдельной таблице
- Поддерживать полиморфизм на уровне кода через наследование интерфейсов

## Поток данных

1. **Создание акта**:
   - Создается запись в таблице `documents` с типом `ACT_OF_WORK`
   - Создается запись в таблице `acts` с тем же ID
   - Возвращается объединенный объект

2. **Получение акта**:
   - По ID запрашиваются данные из обеих таблиц
   - Данные объединяются в единый объект типа `IAct`

3. **Подписание/отклонение акта**:
   - Обновляется статус и соответствующие поля в таблице `acts`
   - При необходимости обновляются поля в таблице `documents`

## Проблемы текущей архитектуры

1. **Отсутствие явных внешних ключей** между таблицами `documents` и `acts`
2. **Несоответствие между схемой ORM и SQL-схемой**: некоторые поля в ORM отсутствуют в базе данных
3. **Сложная логика преобразования данных**: необходимы преобразования форматов (например, для поля `signedBy`)

## Рекомендации по улучшению

1. **Добавить явные внешние ключи** между таблицами
2. **Синхронизировать схему ORM и SQL-схему**
3. **Упростить модель хранения данных** для уменьшения необходимости преобразований
